Three connected surfaces

More than a bot command handler.

The repository separates the responsibilities that commonly get hidden inside a single automation script: Telegram operations, a web/API surface, and asynchronous media and delivery work.

Bot runtime

Telegram-facing workflows

The root runtime and handler layer receive updates, route commands, and keep board-specific administrative work close to the delivery logic.

FastAPI site

Community and browser routes

site_tgach contains the FastAPI application, server-rendered templates, static assets, uploads, and browser-facing interactions.

Media pipeline

Asynchronous asset handling

Dedicated import, mirroring, hashing, and tagging paths keep media operations explicit rather than pretending a synchronous bot reply can do everything.

Interactive repository map

Follow the work to its owning surface.

Select a route to see which part of the repository owns the work. The content below summarizes real paths; it is not a simulated service dashboard.

Root runtime

Receive updates with board context.

The root application, handlers, and management modules form the bot-side entry point. They are responsible for command routing and board-aware control paths before work enters delivery or service modules.

  • main.py runs the root bot surface
  • handlers/ holds update and command routing
  • admin_manager.py carries board-oriented admin flows

Async boundaries

Make outbound work observable and retry-aware.

Delivery management, broadcasting, and periodic publication have distinct locations in the repository, making the queueing and scheduling responsibility visible instead of implicit.

  • delivery_manager.py manages delivery state
  • broadcaster.py owns broadcast-related paths
  • periodic_publisher.py holds periodic publication work

Community surface

Serve browser routes from a dedicated application.

The web application is intentionally separate from the root bot process. Its FastAPI entry point owns rendered templates, browser interactions, API routes, uploads, and web-oriented worker paths.

  • site_tgach/main.py is the web service entry point
  • site_tgach/templates/ contains server-rendered surfaces
  • site_tgach/static/ holds browser assets

File operations

Keep media imports and classification explicit.

Dedicated worker modules organize imports, mirrors, hashes, and tagging work. Those routes are part of the application architecture and should be tested as workflows rather than treated as browser-only effects.

  • importer.py handles incoming media paths
  • mirror_worker.py provides mirroring workflows
  • tagging_worker.py houses classification and tagging work

Run the actual service

Pages shows the project; Python runs it.

This site deliberately remains a static, credential-free project surface. The bot and FastAPI application are independently runnable services and need their own environment configuration.

Operational boundaryNever add Telegram tokens, API credentials, session files, local databases, or downloaded media to the public repository or this Pages surface. Use the committed environment contract and keep deployment values outside Git.
Local orientation
# Bot runtime
python main.py

# FastAPI community application
cd site_tgach
python main.py

# Relevant project-wide verification
python run_all_tests.py

Read the surface honestly

What this page does — and does not — show.

The public artifact is designed to provide a strong first impression while keeping runtime configuration, user-generated material, and server-only operations where they belong.

Is this GitHub Pages site the running FastAPI archive?

No. GitHub Pages hosts this static project surface only. The FastAPI application lives under site_tgach and must be started with the project’s own runtime configuration.

Do the tabs show live queues, users, or messages?

No. They are an accessible guide to the repository structure. The page does not query the bot, database, Telegram, media workers, or external services.

Where can I inspect the actual architecture and setup?

Use the repository README for the component map, environment contract, local commands, and verification guidance. The linked source is the authoritative starting point when documentation and executable configuration diverge.
